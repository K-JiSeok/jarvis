### 1-2. 재사용한 기존 구조

| 기존 구조 | 쓰는 곳 |
|---|---|
| `ingest_batch()` (트랜잭션 · 행 단위 결과 · idempotency) | 새 함수가 그대로 부른다. 저장 로직을 다시 만들지 않았다 |
| `normalizeProduct` · `normalizeSearch` · `normalizeKeyword` · `collectedToRows` | 등록 요청도 같은 정규화 · 같은 배치 행 |
| `parseIngestRequest` | 등록 요청의 records 검사 |
| `products_owner_coupang_product_key` · `keywords_owner_normalized_key` (UNIQUE) | 중복 판정 (`ON CONFLICT DO NOTHING` → "기존 상품") |
| `keyword_snapshots.average_price/average_reviews/rocket_ratio/sample_size` | 1페이지 집계 (새 컬럼 없음) |
| `import_rows.payload` | 미등록 상품의 화면 값 (관측 데이터) — 키워드 상세에서 다시 보여 준다 |
| `competitors` (SAME_PRODUCT · SIMILAR · SUBSTITUTE) + 상품 상세 "경쟁상품 후보" | 같은 검색 결과의 등록 상품을 사용자가 직접 연결 (새 관계 타입 없음) |
| `/api/ingest` | 변경 없음 (공통 검사를 모듈로 옮김 · 응답에 `outcome` 필드 추가) |
| 확장 프로그램 로그인 · 토큰 | 변경 없음 (16절) |

### 1-3. DB migration

**1개: `20261008080729_register_products_and_ingest.sql`**

- 새 함수 1개만 추가. 테이블 · 컬럼 · 상태값 · 기존 함수 · RLS 변경 없음
- `SECURITY INVOKER`, anon 실행 불가, authenticated 실행 가능 [확인]
- 이유: "상품 생성 + 검색 데이터 저장"을 한 트랜잭션으로 묶으려면 DB 안에서 두 작업을 같이 해야 한다
  - 앱에서 상품 INSERT → `ingest_batch` 를 따로 부르면 중간 실패 때 상품만 남는다
- **NO_MATCH 상태값은 migration 하지 않았다** (5절)

## 5. Job 상태

### 5-1. 기존 스키마 확인

- `import_jobs.status` check 제약: `PENDING · PROCESSING · SUCCEEDED · PARTIAL · FAILED · ROLLED_BACK`
- `ingest_batch` 판정: 실패 0 → SUCCEEDED, 추가+갱신 > 0 → PARTIAL, 그 밖 → FAILED
- `error_summary` 에 실패 사유별 개수가 남는다 ("PRODUCT_NOT_FOUND 45")

### 5-2. 결정

- **DB 상태값은 바꾸지 않았다.** NO_MATCH 를 DB 에 넣으려면 check 제약 migration 과 `ingest_batch` 판정 변경이 필요하다
- 대신 상태 + 실패 사유로 결과 상태를 나눠 화면 · API 에 보여 준다 (`jobOutcome`)

| DB status | 실패 사유 | 결과 상태 (화면) |
|---|---|---|
| SUCCEEDED | — | **완료** (COMPLETED) |
| PARTIAL | 전부 PRODUCT/KEYWORD_NOT_FOUND | **일부 미등록** (PARTIAL) |
| PARTIAL | 다른 사유 포함 | 부분 성공 (오류 있음) |
| FAILED | 전부 PRODUCT/KEYWORD_NOT_FOUND | **등록 상품 없음** (NO_MATCH) |
| FAILED | 그 밖 (값 오류 · 전체 롤백) | **실패** (FAILED) |

### 5-3. 실제 결과 [확인]

| 경우 | 실제 수집 | API outcome | `/import` 표시 |
|---|---|---|---|
| 1. 전부 정상 저장 | 선택 등록 3회 · 단일 상품 재전송 | COMPLETED | 완료 |
| 2. 일부 PRODUCT_NOT_FOUND | 캠핑의자 (추가 5 · 실패 45) · 노트북거치대 · 캠핑테이블 | PARTIAL | 일부 미등록 |
| 3. 전부 미등록 | 핸드폰거치대 키워드 미등록 (KEYWORD_NOT_FOUND 52) · 캠핑테이블 순위만 (PRODUCT_NOT_FOUND 49) | NO_MATCH | 등록 상품 없음 |

## 9. 발견된 문제 (실제 사용 중 발견한 것만)

1. **(고침) 쿠팡이 패널을 지운다.** 검색 결과 화면이 뜬 지 약 0.5초 뒤 쿠팡이 html 아래 낯선 노드를 지워 패널이 사라졌다 (PHASE 11 때는 시점이 달라 보이지 않았음). 지워지면 같은 요소를 다시 붙이도록 고쳐서, 체크한 상품 등 상태가 유지된다. 실제 Chrome 에서 6초간 계속 붙어 있는 것을 확인했다.
2. **(고침) 검색 칸 별점은 반올림 값이다.** 검색 결과의 별점(aria-label)은 0.5 단위다 (KCJ: 상품 페이지 3.8 → 검색 칸 4). 같은 날 상품 페이지에서 읽은 정확한 평점을 덮어쓰지 않도록 상품 스냅샷에는 넣지 않고 수집 기록에만 남긴다.
3. **(고침) 키워드 상세의 "등록 상품" 수가 많게 나왔다.** 같은 상품의 반복 칸은 상품을 찾기 전에 "건너뜀"으로 처리되는데, 이것을 등록으로 셌다 (2 → 12). 반복 · 키워드 미등록 칸은 "모름"으로 다루도록 고쳐서 패널과 같은 2/40 이 됐다.
4. **같은 날 검색 칸 값과 상품 페이지 값이 섞인다.** 둘 다 출처가 COUPANG_PAGE 라 같은 날 같은 스냅샷 행에 합쳐진다. 가격 · 리뷰는 같은 화면 값이라 문제가 없었지만, 정가 · 할인율은 검색 칸에 없을 수 있다 (NULL 보존이라 지워지지는 않음).
5. **가격이 하루 사이에도 바뀐다.** 자바탭(9531588589)은 PHASE 11 의 14,800원에서 15,800원이 됐다 (쿠폰 변경). 수집 시각이 중요하다.
6. **검색 칸의 "리뷰 없음"은 모른다.** 리뷰가 없는 상품(WHH)은 검색 칸에 리뷰 숫자가 없어 NULL 로 둔다. 상품 페이지에서는 "상품평 (0)"으로 0 을 확인할 수 있다.
7. **"순위 저장 11/11" 숫자가 고른 상품 수와 다르다.** 고른 상품의 모든 칸(광고 · 옵션 반복)을 센 값이라 처음 보면 헷갈린다.
